## 1. 개요

### 1.1 개발목표

(1) 아트가 규격서만 보고 독립적으로 작업할 수 있는 상태를 만듭니다

* 아트가 만든 프리팹을 코드가 그대로 받아 배치할 수 있도록, 코드와 아트 사이의 인터페이스를 문서로 고정합니다
* 규격이 흔들리면 이미 만든 리소스를 다시 만들어야 하므로, 양산 착수 전에 확정 항목을 잠급니다

(2) 아트 작업과 개발 작업을 병렬로 진행합니다

* 코드는 그레이박스 플레이스홀더로 로직을 먼저 완성하고, 아트 리소스가 도착하면 교체만 합니다
* 서로를 기다려서 생기는 유휴 시간을 없앱니다

### 1.2 개발방향

(1) 규격 확정 -> 프로토 1종 검증 -> 양산 순서로 진행합니다

* 파밍 포인트는 쿼터뷰 단차 표현에 R&D가 필요하다고 명시된 항목입니다 ([파밍 아이템 및 포인트 시스템 문서](./파밍_아이템_및_포인트_시스템_v0.0.1.md) 2.4 (1))

    -> 6종을 한 번에 발주하지 않고, 상단 1종을 먼저 엔진에 넣어 검증한 뒤 나머지를 확산합니다

(2) 연출 아트는 문서 확정 이후로 분리합니다

* 파밍 포인트 강조 연출과 상호작용 연출은 문서가 미완성 상태입니다 (파밍 문서 5장)

    -> 지형/오브젝트 등 형태 리소스를 먼저 진행하고, 연출은 후속 차수로 분리합니다

## 2. 아트 착수 전 확정 항목

* 아래 항목이 확정되지 않으면 아트 결과물을 코드가 받을 수 없거나, 받은 뒤 재작업이 발생합니다
* 확정 주체는 기획(규격 결정)과 개발(엔진 수용 가능성 확인)이 함께입니다

| 항목 | 확정 내용 | 미확정 시 리스크 |
|------|-----------|------------------|
| 존 지형 납품 단위 | 블록 타일 / 행 / 존 통짜 중 무엇으로 납품할지 | 제거 연출 단위와 어긋나면 지형 전체 재작업 |
| 소켓 · 스팟 마커 방식 | 코드가 프리팹 내 위치를 찾는 규칙 | 코드가 프리팹을 인식 불가, 전 프리팹 수정 |
| 단위 · 피벗 · 방향 | 1블록 = 1유닛, 피벗 위치, 진행 방향 축 | 배치 시 어긋남, 전 프리팹 피벗 재조정 |
| 낙하 연출 주체 | 코드 트랜스폼 제어 / 애니메이션 클립 | 클립으로 만들면 코드 제어와 충돌 |
| 폴리곤 · 텍스처 예산 | 프리팹 1종당 상한 | 성능 미달로 리테이크 |
| 네이밍 · 폴더 규칙 | 파일명 규칙과 저장 경로 | 자동 로드 실패, 수동 배선 비용 |

!! 소켓 · 스팟 마커 방식과 단위 · 피벗은 프리팹 1종이라도 양산되기 전에 확정해야 합니다. 이 둘은 전 프리팹에 공통 적용되므로 뒤늦게 바꾸면 물량 전체가 재작업 대상입니다.

## 3. 프리팹 인터페이스 계약

* 코드가 아트 프리팹에서 무엇을 읽는지 정의합니다
* 이 계약을 지키면 아트는 형태를 자유롭게 만들 수 있고, 코드는 프리팹 내부 구조를 몰라도 배치할 수 있습니다

### 3.1 단위와 좌표

* 아트 리소스의 기준 단위와 방향입니다

| 항목 | 규격 |
|------|------|
| 1블록 | 1 유닛 (= 1m) |
| 진행 방향 | +z (플레이어는 +z로 전진) |
| 좌우 | x (존 중심선 x = 0) |
| 상하 | y (보행면 y = 0) |
| 프리팹 스케일 | 1, 1, 1 고정 |
| 회전 | 0, 0, 0 고정 |

* 임포트 시 스케일 팩터를 조정해 크기를 맞추지 않고, 원본 제작 단위를 1블록 = 1유닛으로 맞춥니다

    -> 스케일 팩터로 보정하면 프리팹마다 값이 달라져 배치 계산이 어긋납니다

### 3.2 마커 컴포넌트

* 코드는 프리팹 자식에 붙은 마커 컴포넌트를 수집해 위치를 읽습니다
* 마커는 빈 GameObject에 컴포넌트만 붙인 형태이며, 메시를 가지지 않습니다

| 마커 | 용도 | 개수 |
|------|------|------|
| PointSocket | 존과 연결되는 입구 지점. 제거 판정 기준 좌표 | 파밍 포인트당 1개 |
| ObjectSpot | 아이템 오브젝트가 생성되는 자리 | 파밍 포인트당 1개 이상 |

* 마커의 y 좌표는 그 자리의 보행면 높이로 맞춥니다

    -> 오브젝트 스팟의 y가 실제 바닥과 다르면 아이템 오브젝트가 공중에 뜨거나 묻힙니다

* 마커 컴포넌트는 개발이 먼저 제공하고, 아트는 붙여서 위치만 잡습니다

<span style="color:#888888">(마커 컴포넌트 스크립트는 파밍 포인트 구현 단계에서 개발이 작성해 전달합니다)</span>

### 3.3 콜라이더 정책

* 걸을 수 있는 면과 장식을 구분합니다

| 대상 | 콜라이더 |
|------|----------|
| 보행 가능 지형 (존 바닥, 파밍 포인트 바닥, 경사) | 필요 |
| 장식 (배경 매스, 소품, 실루엣) | 없음 |
| 아이템 오브젝트 | 없음 (상호작용은 거리 판정) |

* 콜라이더는 메시 콜라이더 대신 박스 콜라이더 조합을 우선합니다

    -> 지형이 매 존마다 생성·제거되므로 메시 콜라이더는 비용이 큽니다

### 3.4 네이밍과 경로

* 코드가 경로로 로드하므로 파일명 규칙을 고정합니다

| 리소스 | 경로 | 파일명 예시 |
|--------|------|-------------|
| 존 바닥 타일 | Assets/Prefabs/Field/Tiles/ | FloorTile_Normal_01 |
| 파밍 포인트 | Assets/Prefabs/Field/FarmingPoint/ | FarmingPoint_Top_Rare_01 |
| 아이템 오브젝트 | Assets/Prefabs/Field/ItemObject/ | ItemObject_Chest_Hero |

* 파밍 포인트 파일명은 타입(Top / Bottom)과 등급 위상(Normal / Rare / Hero)을 순서대로 포함합니다

## 4. 존 지형 규격

### 4.1 존 크기

* 존은 블록이 모인 덩어리입니다 ([필드 규칙 및 절차 문서](./필드_규칙_및_절차_v0.0.1.md) 2.1)

| 단위 | 크기 |
|------|------|
| 블록 | 1 x 1 |
| 존 | 25 (길이) x 7 (너비) |

### 4.2 납품 단위 권고안

* 개발 권고는 <span style="color:#4488FF">**블록 타일 세트**</span>입니다
* 근거는 다음과 같습니다

* 바닥 제거는 존 너비 전체 x 1블록 두께의 행 단위로 진행됩니다

    -> 존을 통짜 메시로 받으면 제거 시점에 메시를 분할해야 하므로 런타임 비용과 구현 난도가 함께 올라갑니다

* 타일을 조합하면 존 길이나 너비가 바뀌어도 아트 재작업이 없습니다

* 타일 배리에이션을 여러 종 두면 같은 타일 반복으로 생기는 시각적 단조로움을 코드에서 섞어 해소할 수 있습니다

| 납품 방식 | 아트 물량 | 제거 연출 | 규격 변경 대응 |
|-----------|-----------|-----------|----------------|
| 블록 타일 세트 (권고) | 타일 3 ~ 5종 | 행 단위 그대로 | 재작업 없음 |
| 행(7 x 1) 단위 | 행 3 ~ 5종 | 행 단위 그대로 | 너비 변경 시 재작업 |
| 존 통짜 | 존 2 ~ 3종 | 분할 필요 | 길이·너비 변경 시 재작업 |

### 4.3 존 제거 연출

* 바닥은 세 단계 상태를 가집니다 (필드 문서 3.2 (3))

| 상태 | 표현 | 담당 |
|------|------|------|
| 정상 | 기본 상태 | 아트 (타일 형태) |
| 제거 예정 | 흔들림 | 코드 (트랜스폼 진동) |
| 제거 | 아래로 낙하 | 코드 (트랜스폼 낙하 + 기울기) |

* 흔들림과 낙하는 코드가 트랜스폼으로 처리하므로, 아트는 애니메이션 클립을 만들지 않습니다

    -> 타일이 매 프레임 수십 개 단위로 상태 전이되므로 클립 재생보다 트랜스폼 제어가 가볍고 제어가 쉽습니다

* 낙하 시 파편이 필요하면 별도 파티클로 분리해 발주합니다

## 5. 파밍 포인트 규격

### 5.1 구성 요소

* 파밍 포인트는 네 요소로 구성됩니다 (파밍 문서 2.2)

| 요소 | 제작 주체 | 비고 |
|------|-----------|------|
| 파밍 포인트 지형 | 아트 | 4x4 이상 ~ 7x7 |
| 포인트 소켓 | 아트 (마커 배치) | 존과 잇는 입구, 1개 |
| 오브젝트 스팟 | 아트 (마커 배치) | 아이템 오브젝트 자리, 복수 |
| 아이템 오브젝트 | 아트 (별도 프리팹) | 스팟에 코드가 생성 |

### 5.2 타입과 등급 위상

* 배치 위치에 따라 두 타입, 등급 위상에 따라 세 가지 형태를 제작합니다

| 구분 | 종류 | 물량 |
|------|------|------|
| 타입 | 상단(단차 높게) / 하단(단차 낮게) | 2 |
| 등급 위상 | 일반 / 희귀 / 영웅 | 3 |
| <span style="color:#FF4444">**합계**</span> | <span style="color:#FF4444">**타입 x 위상**</span> | <span style="color:#FF4444">**6종**</span> |

* 전설 위상은 별도 제작하지 않고 영웅 위상 파밍 포인트에 함께 배치합니다 (파밍 문서 2.3)

### 5.3 진입과 안전 규격

* 파밍 포인트는 안전지대이며 이동 조작만으로 오르내릴 수 있어야 합니다 (파밍 문서 2.6)

| 항목 | 규격 |
|------|------|
| 진입 경로 | 포인트 소켓과 같은 선상, 입구 1곳 |
| 단차 오르기 | 점프 없이 이동만으로 통과 가능한 경사 |
| 낙사 | 파밍 포인트 안에서는 발생하지 않음 |
| 입구 외 경계 | 막아도 무방 (입구로 시각 유도) |

* 이동만으로 오를 수 있는 경사 상한은 캐릭터 컨트롤러 설정에 종속되므로, 개발이 수치를 확정해 전달합니다

<span style="color:#888888">(경사 상한 각도는 프로토 1종 검증 시점에 확정합니다)</span>

### 5.4 제거 연출

* 파밍 포인트는 포인트 소켓 좌표가 제거 범위에 들어가면 통째로 낙하합니다 (파밍 문서 2.7)

| 상태 | 표현 | 담당 |
|------|------|------|
| 정상 | 기본 상태 | 아트 |
| 제거 예정 | 파밍 포인트 전체 흔들림 | 코드 |
| 제거 | 전체 낙하 | 코드 |

* 파밍 포인트는 단일 프리팹 루트로 흔들리고 낙하하므로, 루트 하위 구조를 자유롭게 구성해도 됩니다

## 6. 아트 산출물과 의존 관계

* 마일스톤 문서 3장의 아트 리소스를 차수와 선행 조건으로 재정리합니다

### 6.1 1차: 형태 리소스

* 규격 확정 직후 착수 가능한 항목입니다

| 리소스 | 물량 | 선행 조건 |
|--------|------|-----------|
| 존 바닥 타일 | 3 ~ 5종 | 납품 단위 확정 (4.2) |
| 파밍 포인트 프로토 | 1종 (상단 일반) | 마커 계약 + 단위·피벗 확정 (3장) |
| 파밍 포인트 확산 | 5종 | 프로토 엔진 검증 통과 |
| 아이템 오브젝트 | 6종 (상자·항아리 x 3등급) | 마커 계약 확정 |

### 6.2 2차: UI 리소스

* 코드 로직과 병렬로 진행 가능하며, 기존 그레이박스 UI를 대체합니다

| 리소스 | 물량 | 선행 조건 |
|--------|------|-----------|
| 가방 UI (슬롯, 사용·미사용 칸) | 1식 | 슬롯 개수 확정 |
| 무게 바 (5단계 색) | 1식 | 없음 (수치 확정됨) |
| 무게추 아이콘 (3색) | 3종 | 없음 (수치 확정됨) |
| 아이템 스프라이트 | 종류별 | 아이템 종류 목록 확정 |
| 등급 외곽선 (4등급) | 4종 | 없음 |

### 6.3 3차: 연출 리소스

* 문서 확정 이후 착수합니다

| 리소스 | 선행 조건 |
|--------|-----------|
| 상호작용 모션 (종류별 진행 · 완료) | 아이템 오브젝트 형태 확정 + 캐릭터 리그 확정 |
| 파밍 포인트 강조 연출 (발광 · 이펙트) | <span style="color:#888888">파밍 문서 5장 연출 구성 작성 대기</span> |
| 획득 연출 (흡수 이펙트) | <span style="color:#888888">드랍 문서 8장 세부 작성 대기</span> |
| 압축 연출 | <span style="color:#888888">가방 문서 6.3 작성 대기</span> |

## 7. 게이트 기반 스케줄

### 7.1 게이트 정의

* 게이트는 다음 단계 착수 조건입니다. 통과하지 못하면 후속 작업을 시작하지 않습니다

| 게이트 | 조건 | 승인 |
|--------|------|------|
| G1 규격 확정 | 2장 확정 항목 전부 결정, 마커 스크립트 전달 완료 | 기획 + 개발 |
| G2 프로토 검증 | 파밍 포인트 상단 1종이 엔진에서 진입·상호작용·낙하까지 동작 | 개발 |
| G3 양산 승인 | 확산 5종 + 아이템 오브젝트 6종 발주 확정 | 기획 |
| G4 연출 착수 | 연출 문서(파밍 5장 등) 확정 | 기획 |

### 7.2 주차 스케줄

* 기준 시작일을 W1로 두고, 절대 일자는 목표일 확정 후 매핑합니다

| 주차 | 기획 | 개발 | 아트 | 게이트 |
|------|------|------|------|--------|
| W1 | 규격서 확정, 아이템 종류 목록 | 마커 스크립트, 파밍 포인트 배치·제거 로직 (그레이박스) | 레퍼런스 · 컨셉, 타일 1종 테스트 | G1 |
| W2 | 프로토 피드백 | 아이템 오브젝트 상호작용, 그룹 확률 추첨 | 파밍 포인트 프로토 1종, 타일 세트 | G2 |
| W3 | 양산 발주, 슬롯 개수 확정 | 가방 슬롯 · 버리기 · 무게 압축 | 파밍 포인트 확산 5종 | G3 |
| W4 | 밸런스 1차 | 아트 리소스 교체 통합 | 아이템 오브젝트 6종, UI 리소스 | - |
| W5 | 연출 문서 작성 | 통합 검증, 튜닝 | 상호작용 모션 | G4 |
| W6 | 플레이 검증 | 연출 연동 | 연출 리소스 | - |

* 개발은 W1 ~ W3 구간에서 아트 리소스 없이 그레이박스로 로직을 완성합니다

    -> 아트가 늦어도 게임 로직 검증은 막히지 않습니다

* 아트는 W2 프로토 검증(G2) 전까지 확산 작업을 시작하지 않습니다

    -> 단차 R&D 결과가 6종 형태에 모두 반영되어야 하므로, 검증 전 확산은 재작업 위험이 큽니다

### 7.3 작업량 비중

* 아트 물량의 상대 비중입니다. 파밍 포인트가 가장 큰 덩어리입니다

## 8. 리스크와 확정 대기 항목

### 8.1 리스크

* 진행을 막거나 재작업을 유발할 수 있는 항목입니다

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 쿼터뷰 단차 R&D 실패 | 파밍 포인트 형태 전면 재설계 | 프로토 1종 선행 검증 (G2) |
| 연출 문서 미완성 | 연출 아트 착수 불가 | 형태 리소스와 차수 분리 (6.3) |
| 등급 체계 불일치 | 문서는 4등급, 코드는 3단계 | 코드 4등급 확장 시점 확정 필요 |
| 아트 리드타임 미확정 | 스케줄 절대 일자 산출 불가 | 인원 · 형태 확정 후 매핑 |

### 8.2 확정 대기 항목

* 기획 또는 외부 협의가 필요해 이 문서에서 확정하지 못한 항목입니다

| 항목 | 필요 시점 |
|------|-----------|
| 마일스톤 목표일 | 즉시 (스케줄 절대 일자 산출) |
| 아트 가용 인원과 형태 (사내 / 외주) | 즉시 (주차 물량 산출) |
| 폴리곤 · 텍스처 예산, 타깃 디바이스 | G1 |
| 존 지형 납품 단위 최종 결정 | G1 |
| 아트 제작 도구와 전달 포맷 (fbx / glb 등) | G1 |
| 캐릭터 리그 확정 (상호작용 모션 전제) | G4 |
| 가방 슬롯 개수 (기본 / 최대) | W3 |
| 아이템 종류 목록 (드랍 · 파밍) | W1 |
